# In-process mock review handoff

`MockReviewHandoff` is an optional verifier adapter for a daemon-owned mock engine. The trusted caller supplies two distinct pre-registered run-scoped agent instances, an open dedicated thread, private artifact storage and a synchronous trusted reviewer function. The adapter locates the current attempt's immutable candidate artifact and verifies its bytes. It grants two temporary in-process sessions narrowly scoped to this exchange. The author sends a `review.request` with the candidate artifact; the reviewer claims and reads it, evaluates its bytes, and sends a causally linked `review.finding`; both recipients claim and ACK their deliveries using immutable receipt artifacts. The author reads the finding and returns its verdict to the existing engine, which still records candidate-bound verification and controls completion. A negative finding can cause the engine to run the next supplied correction scenario. Session credentials are revoked after the exchange.

This is a deterministic in-process mock workflow, not live MCP worker communication or proof that a verifier is independently authenticated. The caller must ensure reviewer independence, dedicate both inboxes to this workflow and exclude concurrent senders; the adapter fails if either inbox already has outstanding deliveries or a claim returns an unexpected delivery. An interrupted handoff may leave a leased message, receipt artifact or partial thread. It does not automatically resume across new ephemeral sessions: the task remains blocked by the engine and the operator must reconcile the thread and delivery before any authorized retry. Each step commits separately, and blob publication can leave orphan bytes if a database transaction fails. ACK means delivery processing was recorded; only the engine's candidate-bound verification can complete the task.

The adapter is not wired into the production daemon, scheduler, worker launcher, or human approval path. Do not provision these sessions to untrusted agents or assume worker isolation, restart fencing, or approval authorization from this mock exercise.

Mock handoffs claim each expected delivery through a trusted in-process exclusive-inbox helper. It checks recipient/run authorization, expected message identity and absence of any other pending or leased delivery under the same SQLite write transaction as the claim. A competing send therefore causes rollback and blocks the handoff without leasing unrelated messages. This helper is not exposed by the agent gateway or MCP; like the rest of the handoff, it does not automatically recover an interrupted exchange.
