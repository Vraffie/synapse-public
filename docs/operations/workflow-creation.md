# Mock workflow publication and run creation

The daemon-owned `publish_workflow` command accepts 1–1000 nodes, each with an ID and dependency ID list, and validates uniqueness, references, cycles and a total cap of 10,000 edges. It canonicalizes the definition and stores its SHA-256. Published workflow versions are immutable after migration 0007; a change requires a new version. Existing rows are preserved by the migration. Legacy versions that do not match this mock DAG format or their stored hash cannot create runs; they are not silently reinterpreted.

`create_run` validates the stored definition and hash, then creates a run, tasks, dependency edges, creation events, outbox entries and a queued transition in one idempotent command transaction. It returns the run ID and mapping from node IDs to generated task IDs. Retries with the same principal and idempotency key return the original IDs; reusing that key for a different request fails. Outbox or database failure rolls back all writes. The caller must authenticate and authorize every invocation, including retries, and own the daemon database lock. These primitives do not start workers, create mock scenarios, provide an API, or authorize live providers.

The offline integration test `tests/test_mock_workflow_integration.py` exercises publication, idempotent queued run creation, explicit start, a dependency and correction loop, candidate-bound verification, event replay, and persistence after reopening the daemon database. It supplies a trusted verifier callback and scenario mapping directly; it does not demonstrate authenticated API startup, messaging between workers, crash recovery during execution, or verifier identity enforcement.
