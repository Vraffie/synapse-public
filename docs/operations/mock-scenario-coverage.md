# Mock workflow scenario coverage

`tests/test_mock_workflow_scenarios.py` exercises ten offline scenarios using published DAGs and daemon-owned SQLite: single and dependent success; reviewer disagreement followed by correction; exhausted review rejection; retry and exhaustion after provider failure; a failed prerequisite; six provider streams held active with six running attempts and a seventh task waiting; active worker cancellation; and a process crash while review is in progress followed by conservative recovery. It checks durable task and run states, attempts, verification records and outbox consistency. The crash test terminates the subprocess during verifier execution, after its in-process provider attempt has completed; it does not simulate a live worker crash. It reacquires daemon ownership and explicitly asserts no mock worker survives before recovery; recovery leaves the task blocked rather than retrying it.

These scenarios do not demonstrate M2's full end-to-end acceptance gate. The mock engine is not yet wired to daemon scheduling, scenario selection is supplied in memory, and these tests do not establish automatic session recovery, real process fencing, active-agent MCP messaging, human approval, or independent verifier identity. Message routing and leases have separate tests; this suite does not claim that a mock workflow exchanges messages or uses a reviewed real candidate.
