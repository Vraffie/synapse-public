# Approval binding recheck at execution time

> **Security limit (read first).** Against code running as the same OS user as the daemon (including any agent child), approvals are **not** a security boundary: that code can read `approver.token` and `operator.token` and write the SQLite file directly, so it can forge or delete approvals and audit rows. The checks described here catch mistakes and honest components, not a hostile same-user process. See the [security review](../security/review-2026-11-20.md) (F1, F2). The daemon refuses to enable agent runs unless the operator passes `--allow-same-user-agents`.

`synapse.persistence.approval_binding.verify_approval_for_execution(connection, *, approval_id, run_id, operation, target, candidate_sha256, policy_version, now=None)` is the read-only check that must succeed immediately before any external action. An approved record is not permission to execute; the daemon may proceed only if the approved operation, target, candidate SHA-256, policy version, run and expiry still match what is about to be executed. Pass the values you are about to act on, never values read back from the approval.

On success it returns an `ApprovalGrant` (approval_id, state_version, decided_at, principal, verified_at). The grant is only minted by this module in normal use (an in-process guard against accidental misuse, not against hostile code in the same process or user): direct construction, `dataclasses.replace`, subclassing and pickling raise `TypeError`. Execution code should take an `ApprovalGrant` parameter so it cannot be called without a check. The grant is a point-in-time proof, not a bearer credential, and is not durable; re-verify if execution is delayed or retried. This is an in-process guard against mistakes, not a defence against code that deliberately reaches into module internals.

Every other outcome raises a subclass of `ApprovalNotGranted` whose `.reason` is a `DenialReason`: `not_found`, `wrong_run`, `not_approved` (requested or rejected), `expired`, `binding_mismatch` (operation, target, digest or policy differs), `revoked`, `malformed`. Checks run in that precedence: existence, run, state, record integrity, expiry, binding, then approver separation. Expiry is `expires_at <= now` in UTC even when state is still `approved` (expiration is not automatic). `malformed` covers bad input (including naive `now`), corrupt stored values, a missing decision principal, a missing requester identity (legacy unbound requests) and an approver equal to the requester (defence in depth; the service already prevents this).

The lookup runs in one `BEGIN`/`COMMIT` read snapshot, so a concurrent decision or revocation cannot produce a mixed view; a change committed after the snapshot is only seen by the next check, so keep the window between check and action short. The connection must not already be in a transaction. Nothing is written: no events, outbox or audit rows. No `approval.executed_check` audit entry is recorded, because doing so would require a write transaction and change the read-only contract; callers wanting an audit trail should record one in their own execution transaction citing the grant. No execution service exists yet and deployment remains disabled.

## Environment binding (ADR-022)

`synapse.persistence.approval_environment.verify_approval_for_environment(connection, *, environment, **same_args)` additionally requires the approval to be bound to the environment about to be acted on (allowlist: `STAGING`). Bind with `bind_approval_environment` at request time (inside the command transaction, only while undecided; the table is created by `ensure_schema`, inline, no migration). The binding stores `sha256(domain || candidate || environment)`, is immutable, and is recomputed at check time. A missing, unknown, mismatched or tampered environment is denied (`malformed` for unknown/missing input or corrupt binding, `binding_mismatch` for no binding or a different environment). An approval without a binding (all legacy approvals) never passes this check, while `verify_approval_for_execution` is unchanged. The side-effect ledger key includes the environment. Still no deployment code or wiring.
