# Native operator desktop

Install the desktop extra and run `agent-desktop --state-dir /path/to/private-state-directory` as the operator who owns the daemon. The desktop uses the same private Unix-socket and bearer-token checks as `agentctl`. It polls health and event pages on a background thread, retaining its in-memory event cursor across connection failures and reconnecting automatically. Event display retains the latest 1000 entries; closing the desktop does not stop the daemon. Restarting the desktop starts replay from sequence zero. Polling is not WebSocket replay and no snapshot or retention-gap detection exists yet.

Enter a known run ID to display its task nodes and dependency connections from a consistent run snapshot. The graph and approval list refresh while connected and retain their last results with an unavailable indicator when their requests fail. The approval list supports Previous and Next navigation through ID-ordered pages of up to 100 records. A full page enables Next, which may lead to an empty page; if a page fails, Previous returns to the earlier page. Reopening the desktop refreshes from the beginning. Concurrent inserts before the current cursor may require a full refresh. Graphs above 1000 tasks or 5000 dependencies are not rendered. Approval decisions, message sending and run discovery are not yet implemented. Do not give this client to agents: the operator API grants access to all events and runs.

Each run selection carries a new generation, so late responses or errors from an older selection cannot replace a newer selection, including when the operator returns to the same run ID. Offscreen smoke coverage exercises the desktop against a real local daemon as well as reconnection and stale responses.

The Messages tab displays up to 100 threads and 100 messages per page. Use the Previous and Next buttons with mouse or keyboard to navigate each list. Select a run in the Runs tab, then select a thread in Messages. Changing a thread page clears the selected thread; changing the selection resets message pagination. A full page enables Next, which may lead to an empty page when exactly 100 rows remain. If a page fails to load, Previous can return to an earlier page. Cursors are SQLite row IDs; concurrent deletion and insertion can alter pagination, so reselect the run to refresh from the beginning. Late responses from prior pages or selections are ignored. Message sending is not yet available, and payload display is truncated to 1024 characters.

For a selected queued run, **Start fixed mock fixture** starts the daemon's `fixed-v1` synthetic fixture. It cannot select a provider, command, scenario, verifier or deployment target. The UI reports acceptance separately from the eventual run state and sends the request on its polling thread. If the request fails or its response is lost, retry in the same desktop process uses the same idempotency key. Keys are held only in memory; after closing the desktop, inspect the run state before issuing another start. This control does not approve or deploy changes and is not an independent review of real work.

For a selected running run, **Cancel fixed mock run** requests cancellation of the daemon's fixed synthetic fixture; the daemon rejects runs that are not eligible fixed mocks. A successful request reports "Cancellation requested" until a subsequent run snapshot shows a terminal state. A failed or lost response can be retried using the same in-memory idempotency key in the current desktop process. After closing the desktop, inspect the run state and events before issuing another request; the client does not persist keys or recover a prior pending intent. A stale or unavailable snapshot disables the button. This control does not cancel live CLI providers or perform approval or deployment actions.

Changing the run ID disables both mock controls until the input again matches the inspected run; submitting invalid input clears the selection and fences late responses. Invalid or unavailable run snapshots do not enable mock actions.

An offscreen integration test starts a real daemon and a dependency-ordered mock run, closes the first window while a test-controlled provider delay keeps work active, lets the separate daemon process finish, and opens a new window in the same Qt process. It compares the displayed run state, task labels/states, dependency arrow endpoints and direction, and event sequence list with the daemon snapshot and event page. This does not establish complete reconstruction of every persisted field: task IDs, versions, attempts, artifact details and event payloads are not fully represented by the graph, the view has rendering bounds, and event retention-gap detection remains unavailable.

For a recovering built-in `fixed-v1` mock run, **Inspect fixed mock recovery** loads the run and task/attempt snapshots and displays their exact states, versions, fixture/profile and proposed reconciliation request. The operator must explicitly check the assertion that the fixed fixture has no external effects before submission. Selection, run version and displayed task versions are checked again when the dialog closes; the daemon independently rechecks all evidence and worker-stop conditions in its transaction. An accepted receipt does not mean the run finished. If a response is lost, retry in the same desktop process reuses the identical confirmed evidence and idempotency key; no retry occurs automatically. This UI cannot establish human identity, authorize approvals or deployment, or recover a live provider. Closing the desktop loses the pending key; inspect the run and audit trail before making a new request.

If the daemon definitely rejects the fixed-mock resume with HTTP 409, **Discard rejected recovery and reinspect** explicitly clears that rejected intent so the operator can load and confirm fresh evidence. The button is unavailable for timeouts, disconnects or other ambiguous outcomes: those retain the original evidence and key for same-intent retry. Do not discard or retry with a new key merely because a response was lost.
