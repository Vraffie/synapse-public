# Trusted approval service boundary

Migration 0010 adds stable requester subject and kind to approval requests. Existing records remain unbound and the service refuses to decide them; create a new request with an authenticated requester rather than retroactively assigning identity. Request binding fields cannot be updated, deleted or replaced. The low-level repository retains its legacy unbound creation interface for compatibility; it is not an authorization boundary and must not be exposed to untrusted callers.

`ApprovalService` is an internal daemon component with an injected trusted authority. Its authentication context must hold revocation stable for the entire operation and return a stable, globally comparable subject and its actual human or agent kind; the caller cannot select either. The authority must independently authorize the complete request or decision resource, including run, operation, target, candidate hash, policy version, requester and expiry. Decision requires a human subject different from the requester, matching operation/target/hash/policy and unexpired request. Request and decision events, outbox, idempotency receipt and successful audit entry commit atomically. Authorization is rechecked on every retry, including a replay. A replay is a historical decision receipt, not authorization to execute; a future execution service must recheck current approval state, expiry, candidate, target and policy at the point of use. Failed or denied operations do not currently write durable denial audit entries.

No actual human authentication adapter, worker isolation, API route, human approval UI or execution service is provided. A same-user operator bearer token is not proof of a human. Do not wire this service to that token or agent-accessible MCP tools. The integration must establish independently authenticated human identities, protect credentials from workers, distinguish requesters in one authoritative identity namespace, and undergo independent security review. Production deployment remains disabled. Migration rollback is not supported by the current runner; restore from a consistent backup if necessary.
