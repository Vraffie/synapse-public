# Synthetic mock cancellation

An authenticated local operator may POST `/api/v1/runs/{run_id}/mock-cancel` with an `Idempotency-Key` and `X-Correlation-ID`. The command accepts no body and applies only to an actively running built-in fixed-fixture mock run. The response is `202` with `state: cancellation_requested`: it acknowledges a durable request, not worker termination. Reusing the same key replays that receipt; a different key for the same pending request conflicts. Poll the run snapshot for the terminal result.

Migration 0011 adds immutable cancellation intents without changing existing runs. The daemon atomically commits the intent, idempotency response, event and outbox before requesting cancellation of its in-process mock worker. It waits up to five seconds for the orchestration task and its children to stop. Only after they have stopped does a single transaction reconcile unresolved mock attempts, cancel remaining tasks and transition the run to cancelled. Already completed or failed tasks remain unchanged. Synthetic unknown outcomes are recorded as cancelled after stop with an explicit `outcome: discarded` event; these fixed mock workers have no external effects. Mixed or non-mock ownership, inconsistent states, a worker that does not stop, or persistence failure leave the request incomplete rather than asserting cancellation. Cancellation never applies to real CLI providers.

On daemon restart, exclusive ownership establishes that the previous in-process mock workers cannot survive. A pending intent is finalized without relaunching work. The reconciliation transaction rolls back on any error, so startup fails closed rather than hiding unresolved or non-mock work. A hard crash between request and finalization is thus recoverable. An accepted receipt is not a completed cancellation, and there is no automatic deadline-based forced termination or live process fencing here.
