# Delivery leases

The daemon claims pending or expired deliveries with fresh lease tokens, increments the attempt count, and writes delivery state changes with events and outbox entries in the same caller-owned transaction. Expired leases may be redelivered; consumers must handle at-least-once delivery. ACK or NACK requires the current recipient, token and unexpired lease. ACK additionally requires an existing result artifact. NACK returns the delivery to pending or dead-letters it at the configured attempt limit; expired exhausted deliveries are dead-lettered during subsequent claims. Claim processes a bounded batch of exhausted records separately, so they cannot hide eligible deliveries.

Callers must use `BEGIN IMMEDIATE` for claims and completions, roll back on errors, and supply a consistent retry policy. They must authenticate and authorize the recipient and result artifact before invoking these primitives. Use `complete_delivery_idempotently` to replay lost ACK or NACK responses. The authenticated application must authorize the recipient and result artifact on every call, including replays. The durable request hash binds recipient, delivery, lease token, outcome, artifact and retry policy; the response and state change commit together. Server time is excluded so retries replay after lease expiration. Dispatcher wakeup and dead-letter escalation remain application responsibilities; a dead-letter batch may need subsequent polling to process the remainder.

The authenticated gateway and MCP `get_inbox` require an idempotency key for every claim. Trusted in-process service callers may use the older non-idempotent method. The first claim and its lease-token response commit together. A retry with the same session, key and parameters replays the same response only while every returned lease is still current and unexpired; otherwise it fails and the client must start a new poll with a new key. An empty result is replayed as empty, so every new poll requires a new key. Tokens are stored in the private daemon database's idempotency response as well as delivery state. Session revocation still denies retries. Keys are scoped to the current ephemeral session, so retries do not survive credential reissuance or daemon restart until stable session recovery is implemented.

Replay checks are a point-in-time observation: a lease can expire, be NACKed, or be reclaimed after the daemon checks it and before the recipient receives the response. Clients must respect the lease deadline and treat successful completion as authoritative only after ACK succeeds. The completion operation checks recipient, current token and expiry in the same daemon write transaction before updating; stale tokens cannot acknowledge a newer lease. An idempotent claim does not provide exactly-once processing.
