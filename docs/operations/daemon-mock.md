# Daemon-owned mock execution

The private operator API accepts an empty `POST /api/v1/runs/{id}/mock-start` with the same bearer, idempotency and correlation headers as other commands. A queued run starts at most one managed mock run per daemon, with up to six concurrent tasks, using only the fixed `fixed-v1` synthetic fixture and a separately implemented deterministic exact-byte check. The fixture and mock profile are persisted with the run; the client cannot supply a provider, command, scenario or verifier. This checks only the synthetic fixture and is not an independent agent review of real work. No live CLI is executed.

The launch intent and queued-to-running transition commit before background execution; identical retries replay their response and do not launch another engine. On an unclean shutdown or launch gap, the next daemon startup under the database ownership lock marks interrupted running attempts unknown, blocks assigned, running and verifying tasks or other unresolved mock work, and changes the managed run to recovering. It never automatically retries ambiguous work. Recovery uses the conservative mock-only recovery primitive before recording the run transition; a crash between these transactions is safe because startup repeats recovery. Startup checks every managed run, including paused and terminal runs, and fails closed on inconsistent unresolved work. A stopped or blocked run needs a future reconciliation workflow. With the default daemon-owned socket, a hard-killed daemon can leave its socket behind; startup refuses to remove an existing socket, so an operator must verify ownership and remove it before restart. The daemon creates a private artifacts subdirectory in its private state directory. A crash can leave orphaned blobs; reference-aware cleanup is not implemented.

This API is operator-only, not safe for agents. The bearer credential identifies an OS user with the state directory, not a distinct human, and same-user worker isolation remains unfinished. Execution is in-process, so no live process fencing or durable worker resume is provided.

A trusted supervisor can retain the daemon listener and restart it with `--socket-fd`, avoiding manual stale-socket removal; see [local API operations](local-api.md). The supervisor and socket permissions must be configured by the operator, and mock recovery still marks ambiguous work unknown rather than automatically retrying it.
