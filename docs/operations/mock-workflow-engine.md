# Mock workflow engine

`MockWorkflowEngine` executes a running, pre-created run with deterministic mock scenarios, task dependencies, up to six worker slots, durable task/attempt transitions, bounded retries, cancellation of active workers, and an injected independent verifier. It does not execute live providers. The caller owns the daemon lock and database connection, supplies a scenario tuple for every task, and must ensure that the verifier is independent and examines the candidate bytes; this component does not establish verifier identity or authorization. Scenario tuples select the corresponding attempt, falling back to the last item, and must be supplied again on restart. A rejected review retries up to the configured limit; after exhaustion the task stays `changes_required` for operator action.

Output is bounded and persisted as a content-addressed artifact before verification. A passing verifier records the candidate hash and artifact ID and transitions the task to completed in the same transaction as the verification event and outbox record. A verifier error blocks the task; no completion is fabricated. Provider failure is retried only within the configured attempt limit. A missing terminal event, unexpected exception or cancellation of the orchestration coroutine records an unresolved attempt as `unknown` and blocks the task. Unknown outcomes are never retried automatically. Attempt and task transitions, their events and outbox rows share a transaction. Blob publication precedes artifact metadata, so failures can leave unreferenced blobs.

Run setup, authenticated control, approvals, question/reply routing, process fencing, persistent scenario definitions, restart reconciliation and daemon integration remain separate work. A run with unresolved or dependency-blocked tasks returns `blocked` and remains running for operator reconciliation; it is not a successful workflow. This engine only cancels active mock tasks, not waiting tasks. The caller must not infer external process fencing or use this as evidence that the M2 end-to-end gate is complete.

While a run is paused or cancelled, the engine stops scheduling and cancels its in-process workers; interrupted tasks are conservatively blocked rather than silently resumed. After workers stop, it also reconciles reservations whose coroutines were cancelled before their first instruction, leaving those attempts unknown. The verifier and artifact checks bind the candidate hash and provenance to the task and run, but authorization and verifier independence remain caller responsibilities.

A task already at its attempt limit cannot be claimed again, even if its state is manually reset to ready. Generic `verifying → completed` writes are rejected; the verified transition requires an approved result from the claimed verifier and an artifact whose hash and provenance match the task's current completed attempt. Operator approval transitions and other task completion paths need their own candidate-bound authorization before exposure.

Generic `awaiting_approval → completed` transitions are also rejected until a candidate-bound approval execution service is available. Other approval-state transitions retain their existing behavior.

Migration 0008 binds each new verification result to the exact candidate artifact and task attempt, and makes verification results immutable. Existing results survive upgrade with null bindings and cannot authorize task completion; they require fresh verification. This prevents reuse of an earlier approval for identical bytes from a later attempt.
