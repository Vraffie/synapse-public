# Scoped message application service

`MessageService` is a trusted daemon component, not an authentication mechanism or an MCP gateway. An authenticated transport must supply the principal from a verified session, never from message parameters. A trusted server-side `MessageAuthority` maps that principal to exactly one agent instance and run and checks every named capability; callers cannot choose sender or claiming recipient identity. The service verifies the mapped instance belongs to the run. The persistence repository also checks that sender, recipients, and open thread share that run and causation belongs to that thread.

Policies must authorize `message.send` on a thread, `message.recipient` for each recipient, `message.artifact` for each outgoing artifact, `inbox.claim` for the instance's **entire inbox**, `delivery.read` and `delivery.complete` for a delivery, `thread.access` for read/completion, `message.read_artifact` for every incoming reference, and `message.result_artifact` for a result. `inbox.claim` is broad: only grant it when all pending deliveries for that instance may be claimed. Failure or revocation denies access; checks run again on idempotent replays. The supplied authority must use current trusted policy and ensure its decisions remain valid for the duration of each synchronous operation; multi-process policy mutation would require transactional authorization or fencing.

Send and completion are idempotent; claim performs a single transaction and returns lease identifiers, which can be used with `read_delivery`. Read and completion only access deliveries owned by the authenticated instance. The caller must configure bounded retry policy and lease duration; these should be server-controlled, not arbitrary untrusted inputs. The service enforces server-configured limits before persistence: by default 65,536 bytes for the JSON-encoded payload as stored, 32 recipients and 32 artifact references. Limits also apply to idempotent replays and can be configured only by trusted server code. A transport must separately cap request bodies before parsing and bound nesting to prevent resource exhaustion before service validation. No transport, credentials, policy store, per-thread message count or question TTL, dead-letter escalation, thread-history listing or active-session MCP delivery is provided here. Until an authenticated adapter and policy are implemented, this service must not be exposed to agents.
