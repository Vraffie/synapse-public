# ADR 019: Privilege boundary between the daemon and agent children

Status: proposed (design only; no code, unit or package changes). Numbering: `main` holds ADR 012-017 (015 from #85, 016 from #95, 017 from #98). 018 may be claimed by the audit hash-chain work, so this ADR uses 019 to avoid a collision; renumber at merge if the owner prefers. Preserves ADR-002/003 (private Unix transport, daemon ownership), ADR 013 (supervisor-owned listener) and ADR 014 (no claim that user namespaces authenticate a human or protect same-user credentials).

Evidence labels: "code" = read in this worktree at `origin/main` (cd2c8c1); "PR #102" = read via `gh pr diff 102` (open, not draft, not merged); "unverified" = not run or not checked here. Nothing below was executed on a real system.

## Context

`docs/security/review-2026-11-20.md` F1, F2 and F7 share one root cause: the daemon, the human's tools and the agent child (`claude` CLI) all run as the same uid, so every secret and every invariant lives inside that uid's trust domain.

- F1: the SQLite file is `0600` and flock-guarded, but both are advisory against a same-uid process. Triggers only constrain code going through this library (`persistence/approval_binding.py`, `migrations_sql/0010`, `0012`, `0013`); `UPDATE approval_requests SET state='approved'` or `DROP TRIGGER` by any same-uid sqlite client defeats them.
- F2: `<state>/approver.token` (`infrastructure/local_approver.py`, `TOKEN_FILE`, `_check` requires only `st_uid == geteuid()` and mode `0600`) and `<state>/operator.token` (`daemon/__main__.py:_operator_token`, read by `cli/__main__.py` with the same uid check) are plain files. `docs/operations/approver-identity.md:8` and `install.md:33` already state the limitation: "any process running as you can read it".
- F7: the child is contained only partially. Since the review, `main` has hardened `providers/claude_cli.py` (code): env allowlist `PATH, LANG, CLAUDE_CODE_OAUTH_TOKEN` (`_ENV_ALLOWLIST`); per-run scratch `HOME`/`CLAUDE_CONFIG_DIR`/tmp under `<state>/claude-run/<uuid>/` (`_make_scratch`, 0700); prompt via stdin; Synapse-owned `--settings` with `Read`/`Edit` deny rules for the state dir and `~/.ssh` etc. (`_settings`, `_DENY_HOME_SUBDIRS`); rlimits CPU/NOFILE/FSIZE/CORE/NPROC and opt-in AS applied in `_preexec` (`setrlimit` in the forked child); `start_new_session=True` with `os.killpg(..., SIGKILL)` for cancel. These are in-process policy of the CLI plus same-uid rlimits. The deny rules are a request to the CLI, not a kernel boundary: any `Bash` allowance or CLI bug that reads `<state>/operator.token` or opens the DB bypasses them. The scratch dir itself lives inside the state dir, so the agent's `HOME` is a subdirectory of the directory that holds the tokens. `NPROC` counts all threads of the uid including the daemon's (`_nproc_limit`).

ADR 014 says user namespaces alone do not authenticate a human or authorize an approval and that same-uid host processes are out of scope. This ADR is the follow-up that decides how to put a real boundary under F1/F2/F7. Two different questions are involved and are kept separate throughout: (1) can the agent read or write daemon state (confidentiality and integrity of tokens and DB: F1, F7); (2) can the agent impersonate the human to the approval API (F2). Options A and C answer (1) and, as a consequence, hide the file token. Option B answers (2) directly even when (1) is not solved.

Current transport facts relevant to all options (code): the daemon serves HTTP over a Unix socket `<state>/agentd.sock`, bound by `daemon/__main__.py:_socket` (bind, then `os.chmod(path, 0o600)`) or inherited from `agentd-supervisor` (ADR 013). `grep` for `SO_PEERCRED`, `getsockopt` and `peercred` across `src/` finds nothing: today no peer credential is ever read. Authentication is the bearer `operator.token` plus, for decisions, `X-Approver-Token` (`api/approval_decisions.py`). `agentctl backup/backup-verify/restore` open the state dir and DB directly in the caller's process (`cli/__main__.py:_backup_command` calls `persistence.backup.create_backup(state_dir, ...)`), i.e. they assume the CLI uid can read the DB. The desktop calls the daemon through `desktop/connection.py` (approver token passed as `approver_token=`). `validate_worktree` requires worktree `st_uid == os.getuid()` and refuses overlap with the state dir.

## Options

### A. Dedicated uid for the daemon, agents as a different uid

Shape: a system user `synapse` (static via `sysusers.d`, or systemd `DynamicUser=yes` with `StateDirectory=`) runs `agentd-supervisor`/`agentd`, owns `/var/lib/synapse` (0700) including `synapse.sqlite`, `operator.token`, `approver.token`. Agent children run as a third uid (`synapse-agent`, or per-run via `systemd-run --uid` transient service/`DynamicUser`) with a private `HOME` outside the state dir, no read on `/var/lib/synapse`, a cgroup scope for `cgroup.kill` and `MemoryMax=`/`TasksMax=`/`CPUQuota=`. The human's `agentctl` and `agent-desktop` stay under the human uid and reach the daemon over a socket.

How existing pieces change:

- `claude_cli.py` scratch/rlimits: the scratch root moves out of the state dir to e.g. `/var/lib/synapse-agent/run/<uuid>` (owned by the agent uid, daemon writes into it via group or by creating it then `chown`, which needs `CAP_CHOWN`; alternative: the transient unit creates it). `_preexec` currently runs `setrlimit` only; it cannot change uid unprivileged, so the daemon would have to either hold `CAP_SETUID` (undesirable) or ask systemd to start the child: `systemd-run --system --pipe --collect -p User=synapse-agent -p ...` over D-Bus (polkit rule authorizing only the `synapse` user for that exact unit class; unverified that `systemd-run` from an unprivileged uid can create system transient units with `User=` under polkit, to be tested). `RLIMIT_NPROC` becomes meaningful because the agent uid has its own process count (today `_nproc_limit` has to guess headroom over the shared uid). The Python `_preexec` rlimits remain as defense in depth; `cgroup.kill` replaces `killpg` as the cancel path, closing the `setsid` escape in F7. Stdin prompt delivery is unchanged. `_place_credentials` copies a credential file from the real `HOME`/`CLAUDE_CONFIG_DIR` of the daemon: the daemon uid has no human `~/.claude`, so the credential must be provisioned to the daemon explicitly (`CLAUDE_CODE_OAUTH_TOKEN` is already in `_ENV_ALLOWLIST`; a `LoadCredential=` file is the systemd-native route). Note the agent must hold the model credential to function, so this boundary never protects the provider token from the agent, only from other agents' reach into daemon state.
- `validate_worktree`: `st.st_uid != os.getuid()` has to become "owned by the daemon uid or the agent uid, with group policy". Worktrees must be writable by the agent uid and readable by the daemon (the daemon runs `git status/diff`, F4/F5). The simplest layout is agent-owned worktrees under `/var/lib/synapse-agent/worktrees` and daemon git invocations with a scrubbed environment and `GIT_CONFIG_NOSYSTEM`/`safe.directory` handling. Daemon-side git on agent-writable repos is the F4 problem in a new place, so F4 hardening must be complete first. Unverified: whether `worktrees.py` creation assumes same-uid ownership (it chmods its root 0700 at line 231, which would exclude the agent uid and must change).
- Socket and peer credentials: the daemon sets `agentd.sock` to `0660` with group `synapse-ctl` (human is a member; agent uid is not), or `0600` owned by the daemon with a separate human-facing relay (more moving parts). `SO_PEERCRED` (`getsockopt(SOL_SOCKET, SO_PEERCRED)`, a `struct ucred` of pid, uid, gid taken at `connect`) gives the kernel-attested uid of the client. Proposed rule: accept the operator surface only from an allowlisted uid set (the configured human uid) and treat the file `operator.token` as obsolete in this mode; the approver surface additionally needs one of the Option B mechanisms because "peer uid == human" says the human's uid, not that a human is present (a human-uid process such as a compromised desktop would pass). Unverified: how to expose the peer uid from uvicorn to the ASGI app; the daemon serves a pre-bound socket through uvicorn, and the ASGI scope carries no peer credentials, so the likely route is an ASGI-server hook on connection start or a thin custom accept loop. Must be proven by a prototype before this ADR is accepted for implementation. Pid in `ucred` is racy and must not be used for authorization.
- Human tools: `agentctl` and `agent-desktop` connect to `/run/synapse/agentd.sock` (socket in `RuntimeDirectory=synapse`, not under the human's state dir). `agentctl backup` must become a daemon API (daemon writes the snapshot to a path the human can read, e.g. `RuntimeDirectory` hand-off, or streams it); `restore` stays offline and root-run (`sudo -u synapse agentctl restore` or `systemd-run`). `desktop/status_bar.py` hard-codes `<state>/agentd.sock` as a label and `cli/__main__.py` derives `state_dir/"agentd.sock"` (code): both need an explicit `--socket` path.
- Arch packaging (PR #102, open, not merged; read from its diff): the package is `arch=(any)`, installs `/usr/lib/systemd/user/synapse-daemon.service` as a user unit with `StateDirectory=synapse`, `ProtectHome=read-only`, `CapabilityBoundingSet=` (empty), `NoNewPrivileges=yes`, `RestrictAddressFamilies=AF_UNIX`; `synapse-agent-control.install` is messages-only, and `docs/operations/arch-package.md` promises "it never starts anything and never touches user data". Option A needs: a system unit `/usr/lib/systemd/system/synapse-daemon.service`, `/usr/lib/sysusers.d/synapse.conf`, `/usr/lib/tmpfiles.d/synapse.conf`, a polkit rule, and a changed `.install` that is still messages-only (users are created by the `sysusers` pacman hook, which is the Arch convention and needs no code in `.install`). The existing user unit would remain as the "unbounded, same-uid" mode. `tests/test_arch_package.py` asserts the packaged user unit's hardening equals the per-user unit; a system unit would need its own such test. `CapabilityBoundingSet=` empty on the daemon forbids it from `CAP_SETUID`; the child must therefore be started by systemd (above), which fits.
- Stops: F1 (agent uid cannot open the DB or its WAL/SHM files), F2 as a file-theft attack (agent cannot read `operator.token`/`approver.token`), F7 state dir exposure and `setsid` escape (cgroup kill), `/proc/<pid>/environ` of the daemon (`hidepid`/different uid; unverified that `/proc` hidepid is not needed since cross-uid `environ` reads are already denied by ptrace/proc permission rules).
- Does not stop: a root or `synapse`-uid compromise; kernel bugs; the agent talking to the daemon through any channel the daemon deliberately exposes to the agent uid (the MCP gateway socket, `mcp_gateway/ipc.py`, `0600` today, would need its own peer-checked socket with limited methods); approval by the human's own uid if that uid is compromised (desktop, `agentctl`, or a terminal the agent can type into); the agent's own network egress (needs `IPAddressDeny`/nftables per uid; the agent needs the Anthropic API so allowlisting by uid is a separate task); and, importantly, the human uid's own files: the agent uid is also not the human uid, so `~/.ssh` is unreadable by DAC, which is a F7 win, but worktrees of the human's repos need an explicit sharing design.
- Install and daily cost for one developer on Arch laptop: `sudo pacman -U`, `systemctl enable --now` as root, add self to `synapse-ctl` group and re-login; two or three new uids; debugging requires `journalctl -u`, `sudo -u synapse` or `machinectl`; file sharing between the human's repos and agent worktrees (clone via the daemon, human reads agent output through `git fetch` from a bare/shared path) is the main daily friction; `claude` credentials must be re-provisioned for a service uid (no browser login). Loses the "no root ever" property of M7.3.
- Migration from today: state dir `~/.local/state/synapse` to `/var/lib/synapse` through `agentctl backup` (offline file), `restore` into the new location (works, DB-only per `arch-package.md`; the F8 caveat about triggers applies, check `backup-verify` after restore), regenerate tokens (they are never in backups). Run old user unit and new system unit never together (two daemons, two DBs). A `--mode user|system` selector keeps both supported.
- Testability: unit-level (no root): path/permission policy functions, peer-credential parsing from a `struct ucred` over `socketpair(AF_UNIX)` (pid/uid are the test process's own; proves the plumbing but not cross-uid), unit file lints (`systemd-analyze verify`, `systemd-analyze security --offline`), packaging static tests like `tests/test_arch_package.py`. Real proof needs root or a VM/container: a test that `su`/`setpriv --reuid` to the agent uid cannot `open(state/synapse.sqlite)` (EACCES) or `connect` to the socket, and that a `systemd-run -p User=` child dies by `cgroup.kill`. These can run as an opt-in `SYNAPSE_PRIV_TESTS=1` module in the same style as `tests/test_claude_cli_real.py` (skipif on env var), in a throwaway systemd-nspawn or rootless-podman-with-systemd container, never in default CI (Actions minutes are limited).
- Failure modes: misconfigured group (human locked out, fails closed); daemon uid and agent uid accidentally equal (must be a startup check comparing `geteuid()` against the configured agent uid, refusing to enable the agent runtime, as F2 already recommends for token readability); a leaked `synapse-ctl` membership grants operator power; polkit rule too broad lets any local process start agent units; `DynamicUser` reuses uids across restarts and chowns state on start (fine for state under `StateDirectory`, but persistent files elsewhere become orphaned); `RLIMIT_NPROC` set per uid is shared with other processes of that uid.

### B. Human-presence approval so the approver secret is not an agent-readable file

Addresses F2 only. Variants:

1. polkit prompt: the daemon (or a tiny privileged helper) calls `org.freedesktop.PolicyKit1` `CheckAuthorization` with an action id like `org.synapse.approval.decide` and `AllowUserInteraction`. The desktop environment's agent shows the password dialog on the human's session. Pro: no new hardware, native Arch (polkit is present on KDE/GNOME desktops; unverified on this laptop). Con: polkit authorizes a subject (pid/uid/session) for an action, and the details dict is displayed text, not a cryptographic binding to the approval hash; an agent that can run processes in the same session and has the same uid can call the same API and hope the human clicks (a confused-deputy/prompt-fatigue attack). It proves "a human typed their password for action X at some moment", only when the dialog shows the binding hash and the human reads it.
2. FIDO2/WebAuthn assertion bound to the binding hash: at enrollment the daemon stores only the credential id and public key (a verifier). At decision time the daemon issues `challenge = SHA-256(approval_id || candidate_sha256 || operation || target || policy_version || state_version)` (the fields already carried by `DecisionRequest` and checked in `persistence/approval_binding.py` and `approval_service.py`; exact field list and canonical encoding to be taken from `approval_binding.py`, not re-derived here); the human's authenticator signs it after a physical touch (CTAP2 `getAssertion`, `userPresence`, optionally `userVerification`); the daemon verifies the signature with the stored public key and checks the signature counter. The secret never exists on disk; the agent cannot forge a signature without touching the key. Needs a library (`python-fido2` in Arch repos as `python-fido2`, unverified) and a USB/NFC key; running the CTAP exchange from a CLI/desktop process under the human uid needs `hidraw` access (udev `uaccess`, normally fine for the logged-in user). Con: requires hardware the owner may not have; a same-uid agent can still start a request but not complete it; a compromised desktop UI could show a different text than the hash it asks the key to sign, so the UI must display the same fields it hashes (the hash alone is opaque, which is F6's concern).
3. Trusted UI process with a typed secret, daemon holds only a verifier: the human sets an approval passphrase; the daemon stores a memory-hard verifier (argon2id/scrypt, `hashlib.scrypt` is in the stdlib) and the desktop/CLI prompts via a TTY/Qt dialog and sends the passphrase (or better, a PAKE/HMAC response to a daemon challenge so the passphrase never travels). Pro: no hardware, no root, small code (replaces `LocalApproverAuthority._current`, which today reads `approver.token`). Con: a same-uid agent can still keylog or ptrace the desktop process (Yama `ptrace_scope` default on Arch is 1, which blocks ptrace of non-children but not `/proc/<pid>/mem` tricks via the same parent chain; unverified here), can read terminal contents, or hijack `agentctl` through `LD_PRELOAD`/`PATH` in files it can write (`~/.bashrc`); and an offline attack against the verifier is possible if the DB is readable (it is, F1). So B3 on its own is only as strong as the uid boundary; it removes the readable bearer file but not shoulder-surfing by a same-uid process.
- Stops (F2): theft of a static approver token from disk; with FIDO2 also replay and off-box approval-by-forging (signature bound to the binding hash and to a counter). Does not stop: F1 (the agent writes `state='approved'` straight into SQLite; verifier or not, the DB is the authority, so B is worthless against F1 unless the DB is out of reach), F7 (state-dir exposure, `setsid`, resource abuse), or a same-uid agent that edits the human's `~/.bashrc`, autostart files or desktop launcher to run a malicious approver (B1/B3). FIDO2 survives even that, because the physical touch and the signed digest are outside the uid.
- Install and daily cost: B1 needs polkit rule/policy files and a prompt per approval (cheap, but trains click-through). B2 needs a key (about 30-60 USD) and a 2-3 second touch per approval, and enrollment/recovery flow (lose the key: need a break-glass reset requiring offline DB or root). B3 needs one passphrase entry per approval, typed password fatigue.
- Migration: add a new `ApprovalAuthority` implementation beside `LocalApproverAuthority` (the interface `authenticated(credential) -> Actor` and `allows(...)` exists and `approver-identity.md:8` says the file token is "replaceable by stronger proof of presence behind the same interface"). The decision endpoint currently requires a 43-character token header by regex (`api/approval_decisions.py:_TOKEN`) so the wire format changes (new header or JSON field for the assertion, challenge endpoint). Keep the old token path behind an explicit "weak" setting that refuses to enable the agent runtime when it is enabled and unsandboxed.
- Testability: B2 and B3 are fully unit-testable without root: signature verification with a software authenticator (python-fido2 ships a virtual/soft authenticator helpers for tests; unverified) or a test ECDSA key; binding tamper tests (change `candidate_sha256`, assertion fails); replay (counter) tests; verifier compare timing. What cannot be proven by tests: that a human was physically present. B1 testability is poor without a polkit session (mock the D-Bus service; the real thing is manual).
- Failure modes: lost authenticator (recovery policy needed), clock/counter desync, UI displays text different from the hashed fields, authenticator not plugged in (approvals block; today's agent gates park, which is a safe default), prompt fatigue.

### C. User-scope sandbox without a second system user

Shape: keep one uid. Launch the agent child inside a sandbox that hides the state dir and the real `HOME`: (C1) `systemd-run --user --scope`/transient service with `ProtectHome=tmpfs`, `BindPaths=<worktree>`, `InaccessiblePaths=<state dir>`, `PrivateTmp`, `NoNewPrivileges`, `MemoryMax=`, `TasksMax=`, `RestrictAddressFamilies`, and `KillMode=control-group` (cgroup kill, closing the `setsid` escape); (C2) `bubblewrap` (`bwrap`), reusing the launcher style of ADR 014 (new mount/PID/IPC/UTS namespaces, tmpfs home, read-only `/usr`, bind of one worktree at `/work`; ADR 014 already ships such a launcher for the mock worker, `tests/test_mock_sandbox.py`, so the real-provider variant would reuse it with network allowed and a credential mount); (C3) Landlock via `landlock_create_ruleset` (kernel 5.13+, this machine reports 7.3; the Python stdlib has no wrapper, so a ctypes call in `_preexec` or a tiny helper; unverified in this repo) restricting filesystem access to the worktree and scratch dir without a mount namespace.
- How `claude_cli.py` changes: `_make_scratch` keeps working but the scratch root should move outside `<state dir>` (it is currently `<state>/claude-run/<uuid>`) so that hiding the state dir does not hide the agent's `HOME`; `_settings` deny rules become a second layer under a kernel-enforced first layer; `_preexec` rlimits stay; `_spawn` wraps `argv` with the launcher; `killpg` is complemented by `cgroup.kill` (C1) or PID-namespace teardown (C2); `validate_worktree` is unchanged (same uid).
- Stops: F7 state-dir and `~/.ssh` exposure through the child's file access (kernel-enforced, not just CLI deny rules), `setsid` survival (C1/C2), resource abuse (C1 cgroup limits). F1 and F2 against an agent that stays inside the sandbox: it cannot see `agentd.sock`'s directory, the DB or the tokens if they are not bind-mounted or visible, so file theft and direct SQLite writes fail by path invisibility.
- Does not stop (honest limits): everything is still one uid. Any escape from the sandbox (a kernel LPE; a user-namespace-reachable bug; a bind mount mistake; an allowed `Bash` that uses a path the sandbox exposes such as `/run/user/$UID/bus`, `$XDG_RUNTIME_DIR/*`, an X11/Wayland socket, an SSH agent socket, or `/proc/<daemon-pid>/{environ,mem,fd}` of a same-uid process if `/proc` is not a private PID-namespace mount) lands as the same uid with full access to the tokens and DB. Systemd user transient units give no uid separation: from inside, `systemctl --user` and the user D-Bus session (if reachable) can start unconfined units. C1 without `PrivateUsers`/mount namespaces still shows the same-uid `/proc` to the child, so ptrace/`/proc/<pid>/mem` of the daemon is limited only by Yama and `dumpable` (unverified). Landlock (C3) restricts file access only, not `connect()` to Unix sockets by pathname on older ABIs, and not signals or ptrace (ABI-version dependent, unverified here). Any other process running as the human (browser, a malicious package install) is not contained at all. The sandbox must also not be disabled by an agent-writable config (the profile and any launcher path must live outside agent-writable locations; the repo-config refusal in `_check_repo_config` already addresses one vector).
- Install and daily cost: lowest. `bubblewrap` is in Arch `extra` (unverified on this laptop); no root after install; unprivileged user namespaces must be enabled (`kernel.unprivileged_userns_clone`/Arch default is enabled, unverified; ADR 014 already depends on this). C1 additionally needs a working user manager session (the existing unit runs under `systemd --user` already, but `systemd-run --user` from inside the daemon's own sandboxed unit with `RestrictNamespaces=yes`, `NoNewPrivileges=yes`, `ProtectHome=read-only` is likely to conflict: `RestrictNamespaces=yes` in the packaged unit blocks bubblewrap's `unshare`, so the unit must be relaxed for the daemon, a real regression of the PR #102 unit's hardening, or the launch must go through the user manager, unverified).
- Migration: purely additive and opt-in via a profile flag, no state move.
- Testability without root: good. `tests/test_mock_sandbox.py` (ADR 014) is the model: run a real `bwrap` and assert that inside the sandbox `open(<state>/operator.token)` fails with ENOENT/EACCES, that `HOME` is empty, that a `setsid`-spawned child dies at teardown, that `/proc/<outside pid>` is invisible, that a process cannot `connect` to the daemon socket. Skip with an explicit reason when `bwrap` or unprivileged namespaces are missing. A fake `claude` script that tries to read the tokens is a sufficient subject; the real CLI is not needed (the existing real test is opt-in via `SYNAPSE_REAL_CLAUDE=1`). Landlock can be tested the same way in a forked child. C1 can be tested with `systemd-run --user` only when a user manager is available (skip otherwise).
- Failure modes: fail closed when the launcher is missing (as ADR 014 does, no unsandboxed fallback); the provider CLI may need paths the sandbox hides (credentials, `~/.claude.json`, node, certificate stores), producing "works unsandboxed but not sandboxed" breakage that is only found against the real `claude` (unverified); kernel/namespace hardening differences across Arch updates; sandbox escape lowering to full compromise with a false sense of safety; stale cgroup scopes.

## Comparison

| | A dedicated uid | B human presence | C user-scope sandbox |
|---|---|---|---|
| F1 SQLite direct write | stopped (DAC) | not addressed | stopped only while the agent stays sandboxed |
| F2 token theft / self-approval | stopped (token unreadable); approval still needs B | stopped (FIDO2 strongest) | stopped only while sandboxed |
| F7 state dir, HOME, setsid, rlimits | stopped | not addressed | mostly stopped (kernel-enforced file view, cgroup) |
| Survives same-uid code execution outside the sandbox | yes | FIDO2 only | no |
| Needs root to install | yes | polkit files: yes; FIDO2/passphrase: no | no |
| Daily friction | highest (shared files, creds, groups) | one touch or prompt per approval | low |
| Testable without root | partly (policy yes, boundary no) | yes (crypto), not presence | yes (bwrap/Landlock) |

## Decision (proposed)

Adopt a layered path, in this order, each step independently useful:

1. Build C2 first (bubblewrap launcher for the real provider, state dir and real `HOME` invisible, scratch root moved out of the state dir, PID-namespace teardown), because it is buildable and provable without root, reuses ADR 014, and removes the cheapest attacks (F7, and F1/F2 for a non-escaping agent). State plainly in `docs/security` and operations docs that it is a same-uid mitigation, not a boundary.
2. Build B2/B3 behind the existing `ApprovalAuthority` interface so approval no longer depends on a readable file. Prefer FIDO2 if the owner has a key; otherwise B3 with a verifier, explicitly labelled as only as strong as the uid separation.
3. Treat A as the target architecture for the only complete fix, as an opt-in "system mode" delivered after steps 1 and 2 (a system unit, sysusers/tmpfiles, peer-credential socket authentication, daemon-mediated backup). It is what F1 actually requires: F1 cannot be fixed by B or C alone.

Until A exists, the agent runtime must keep refusing to start when `approver.token` or the DB is reachable by the agent's uid, as F2 recommends, and user-facing text must not call approvals human-only.

## Minimal first slice (no root)

1. A launcher module (`synapse/providers/sandbox_launcher.py` or reuse ADR 014's) that wraps the `claude_cli.py` argv in `bwrap` with: tmpfs `HOME`, scratch dir bind outside the state dir, one worktree bind at `/work`, read-only `/usr`, private `/proc`, `--unshare-pid --unshare-ipc --unshare-uts`, `--die-with-parent`, network left shared, an env allowlist (unchanged). Opt-in via `ClaudeCliProfile` field; refuses to start if `bwrap` is missing; no unsandboxed fallback.
2. Tests with a fake agent script (no network, no API quota): reads of `operator.token`, `approver.token` and `synapse.sqlite` fail; the scratch `HOME` is the only writable home; a `setsid` grandchild is gone after cancel; `/proc` shows no host PIDs; skip when bwrap/userns unavailable.
3. A startup check that compares the agent's effective uid to the state dir owner and logs/refuses when no sandbox is configured and the agent runtime is on (a pure function, unit-testable).
4. A peer-credential prototype: read `SO_PEERCRED` on an accepted Unix socket in a test using `socketpair`, and decide how uvicorn exposes it. No behavior change in the daemon.
5. Docs only: update the threat-model text in `approver-identity.md` and `install.md` accordingly.

## Non-goals

- Defending against root, the kernel, or a compromised human uid.
- Network egress policy for agents, secrets management for the provider credential, multi-user or multi-host operation.
- Replacing the in-process mock engine (ADR 014) or changing the HTTP API and token format in the first slice.
- Fixing F3-F6, F8-F13 (separate findings; A depends on the F4/F5 git hardening landing first).
- Shipping system units or touching PR #102's packaging in this ADR.

## Open questions for the owner

1. Do you own a FIDO2 key (or willing to buy one), and is a touch per approval acceptable? If not, is B3 (passphrase verifier) acceptable as a stopgap?
2. Is root-owned system installation acceptable for your laptop (option A), given it ends the "no sudo ever" property of the Arch package and requires re-provisioning the Claude credential for a service uid?
3. Is the daemon required to keep running after logout (lingering)? A system service does this naturally; the user unit does not.
4. Should the agent be allowed network access at all beyond the model API? That decides whether C needs a network namespace and what A needs in nftables.
5. Are the human's own repos to be worked on in place by agents, or only in daemon-managed clones? In-place work weakens every option.
6. Is ADR number 019 right (018 reserved for audit hash-chain)? And should PR #102 stay user-unit only until this is decided?
7. Unverified items to confirm on the real machine before implementation: `bwrap` and unprivileged user namespaces available; polkit agent running; `systemd-run` as non-root creating system transient units under polkit; how uvicorn exposes peer credentials; `python-fido2` availability.

## Owner decisions (2026-11-20)

Recorded from the owner's answers to the open questions. They fix the order of work; they do not close the design.

1. **FIDO2:** the owner has no FIDO2 key. Human-presence approval therefore starts as the passphrase verifier (option B stopgap), behind the existing `ApprovalAuthority` interface, so a FIDO2 authenticator can be added later without changing callers.
2. **Root-owned system install (option A): not yet.** Build the user-scope sandbox (option C) and the passphrase approval first. Revisit option A before agents run against anything that cannot be lost (for example the STAGING deployment path), or if other people or untrusted repositories are involved. Until then the agent runtime keeps requiring the explicit same-user acknowledgement (`--allow-same-user-agents`, PR #116).
3. **Agent network access:** allowed beyond the model API. The sandbox therefore does not unshare the network namespace by default. Network egress policy stays a non-goal here, and the documentation must say that a network-capable agent can exfiltrate anything it can read.
4. **Working directories:** agents work in daemon-managed clones (per-run worktrees) only. Working in the owner's checkout in place is allowed only behind an explicit, off-by-default feature flag. In-place mode needs its own safeguards (refuse a dirty tree, bind the approval to the checkout's head, never run it under the sandbox's reduced-exposure assumptions), to be specified before it is built.
